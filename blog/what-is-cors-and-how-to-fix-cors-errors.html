什么是 CORS？跨域资源共享完整指南

2026年7月28日 · SiteCheck

如果你做过任何前后端分离的 Web 项目，几乎一定遇到过这样一段刺眼的红色报错：Access to fetch at '...' from origin '...' has been blocked by CORS policy。CORS（Cross-Origin Resource Sharing，跨域资源共享）是现代 Web 开发中最常被误解、却又无法绕开的安全机制。它既不是 Bug，也不是浏览器的"刁难"，而是保护用户数据的一道重要防线。本文将从同源策略讲起，深入剖析 CORS 的工作原理、预检请求机制、核心响应头含义，并给出常见错误的排查方法与 Nginx、Apache、Node.js、Spring Boot 等多种技术栈的实战配置，帮助你彻底搞懂并解决 CORS 问题。

一、同源策略：CORS 存在的根本原因

要理解 CORS，必须先理解同源策略（Same-Origin Policy）。同源策略是浏览器最核心的安全机制，它规定：一个源（Origin）下加载的脚本，默认不能向另一个源发起 AJAX/Fetch 请求读取响应，也不能操作另一个源的 DOM。所谓"同源"，是指协议（Protocol）、域名（Host）和端口（Port）三者完全相同。只要其中任何一个不同，就属于"跨源"（Cross-Origin，习惯上称为跨域）。

举例来说，页面 https://example.com/index.html 与以下地址的关系是：

  • https://example.com/api/data —— 同源（同协议、同域名、同端口）。
  • http://example.com/api/data —— 跨源（协议不同，http vs https）。
  • https://api.example.com/data —— 跨源（子域名不同）。
  • https://example.com:8080/data —— 跨源（端口不同）。

同源策略的意义在于防范恶意网站窃取用户在其他网站的数据。想象一下：如果没有同源策略，你登录了银行网站后，又访问了一个恶意网站，恶意网站的 JavaScript 就能以你的身份向银行接口发请求并读取返回数据，后果不堪设想。同源策略正是为了阻断这种跨站数据读取。

但同源策略也带来一个问题：现代网站常常需要从不同域名加载资源——前端部署在 app.example.com，API 部署在 api.example.com，或者调用第三方公开 API。如果一刀切禁止所有跨源请求，Web 应用将无法正常工作。CORS 正是为了在安全可控的前提下"放开"同源策略而诞生的标准机制。

二、CORS 是什么？它如何工作

CORS 是 W3C 制定的一项标准，它通过一组 HTTP 头部字段，让服务器声明哪些外部源可以访问自己的资源，从而允许浏览器跨源发送请求并读取响应。关键在于：CORS 的检查和拦截完全由浏览器执行，服务器只是按规则在响应中添加相应的头部信息。

CORS 的工作流程可以概括为：浏览器在发起跨源请求时，会在请求头中附加 Origin 字段，标明请求来自哪个源；服务器收到请求后，根据自身的策略决定是否允许，并在响应头中返回 Access-Control-Allow-Origin 等字段；浏览器拿到响应后，检查这些头部是否允许当前源访问，如果允许则把响应交给 JavaScript，否则拦截响应并抛出 CORS 错误。

这里有两个常被忽略的要点。第一，请求实际上已经被发送到服务器并可能执行了后端逻辑，浏览器拦截的是"响应的读取"，而非请求本身。这对敏感操作（如转账、删除）有重要安全含义——不能依赖 CORS 来防止 CSRF，CORS 防的是"读"，不是"写"。第二，CORS 只对跨源的 AJAX/Fetch 请求生效，不影响 <img>、<script>、<link> 等标签的资源加载，这些标签的跨域加载由各自的策略控制（这也是 JSONP 等早期跨域方案的原理）。

根据请求的特征，CORS 将请求分为两类："简单请求"和"需预检请求"，两者的处理流程不同，下面分别详解。

三、简单请求与预检请求

并非所有跨源请求都会触发预检。浏览器对满足特定条件的请求采用"简单请求"模式：直接发送，不预先询问。一个请求要被判定为"简单请求"，必须同时满足以下所有条件：

  • 请求方法为 GET、HEAD 或 POST 之一。
  • 除了浏览器自动设置的头（如 Accept、Accept-Language、Content-Language）外，自定义请求头只能是 Content-Type、Content-Length 等少数安全字段。
  • Content-Type 只能是 application/x-www-form-urlencoded、multipart/form-data 或 text/plain。
  • 请求中没有使用 ReadableStream 对象。
  • 请求中的 XMLHttpRequest.upload 没有注册任何事件监听器。

对于不满足上述条件的请求——例如使用了 PUT、DELETE 方法，或设置了 Content-Type: application/json，或携带了 Authorization、X-Requested-With 等自定义头——浏览器会先发送一个 预检请求（Preflight Request）。

预检请求是一个 OPTIONS 方法的请求，不携带实际数据和业务参数，它的作用是"先问后做"。浏览器在预检请求中带上以下头部：

OPTIONS /api/data HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Content-Type, Authorization

服务器收到预检请求后，返回一个不带实际数据的响应，通过 CORS 头部告知浏览器允许的操作范围：

HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400

浏览器检查预检响应，如果实际请求的方法、头部都在允许范围内，才会发送真正的请求；否则直接报错，真实请求根本不会发出。Access-Control-Max-Age 指示浏览器可以将这次预检结果缓存多久（示例为 86400 秒，即 24 小时），在缓存期内对同一资源的相同请求不会再发预检，能显著减少 OPTIONS 请求。

理解"简单请求"和"预检请求"的区分对排查问题非常关键。很多人困惑"为什么有时看到 OPTIONS 请求，有时看不到"，原因就在于此。如果你用 application/json 发 POST，一定会触发预检；而用表单提交则不会。

四、CORS 核心响应头详解

CORS 的配置全部体现在服务器返回的响应头上。下面逐一解析这些核心字段：

  • Access-Control-Allow-Origin：最关键的字段，指定允许访问的源。可以是一个具体的源（如 https://app.example.com），也可以是 *（表示允许任意源）。注意：当请求需要携带凭证（Cookie）时，Access-Control-Allow-Origin 不能设为 *，必须指定确切域名。
  • Access-Control-Allow-Methods：在预检响应中声明允许的 HTTP 方法，如 GET, POST, PUT, DELETE, OPTIONS。
  • Access-Control-Allow-Headers：在预检响应中声明允许的自定义请求头，如 Content-Type, Authorization, X-Requested-With。
  • Access-Control-Expose-Headers：默认情况下，跨源响应中只有少数"安全"的头（如 Content-Type、Cache-Control）能被 JavaScript 读取。如果想让前端读取自定义响应头（如 X-Total-Count、X-Request-Id），需要在这里声明。
  • Access-Control-Allow-Credentials：设为 true 时，允许浏览器在跨源请求中携带 Cookie 和 HTTP 认证信息。与前端 fetch 的 credentials: 'include' 或 XMLHttpRequest 的 withCredentials = true 配合使用。
  • Access-Control-Max-Age：预检请求结果的缓存时间（秒），减少重复 OPTIONS 请求。

这些头部的取值需要前后端配合。一个常见错误是服务器返回了 Access-Control-Allow-Origin: *，但前端又开启了 credentials: 'include'，浏览器会直接拒绝，因为携带凭证时不能用通配符。这种"看似都配了却还报错"的情况，往往就是头部之间的约束冲突。

五、携带凭证的跨域请求与 Cookie

默认情况下，跨源的 AJAX/Fetch 请求不会携带 Cookie 和 HTTP 认证头，这是浏览器的安全默认行为。如果需要跨域传递 Cookie（例如维持登录态），需要前后端同时配置。

前端（Fetch API）：

fetch('https://api.example.com/user', {
    method: 'GET',
    credentials: 'include'  // 关键：允许携带跨域 Cookie
})
.then(res => res.json())
.then(data => console.log(data));

前端（XMLHttpRequest）：

const xhr = new XMLHttpRequest();
xhr.open('GET', 'https://api.example.com/user');
xhr.withCredentials = true;  // 关键
xhr.send();

后端必须返回：

Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true

这里有三个必须严格遵守的规则，违反任意一条都会导致 CORS 失败：

  1. Access-Control-Allow-Origin 不能是 *，必须是具体的域名（与请求的 Origin 匹配）。这是因为通配符配合凭证会带来安全风险——任何站点都能以用户身份携带 Cookie 访问。
  2. Access-Control-Allow-Credentials 必须显式设为 true。
  3. 跨域 Set-Cookie 受 SameSite 属性约束。现代浏览器默认 SameSite=Lax，会阻止大部分跨站 Cookie 发送。若要跨域携带 Cookie，后端 Set-Cookie 通常需设为 SameSite=None; Secure，这意味着只能在 HTTPS 下生效。

凭证跨域是 CORS 中最容易出错的部分。如果遇到"登录状态丢失""Cookie 传不过去"，首先要检查的就是这三点。

六、常见 CORS 错误信息解读

浏览器抛出的 CORS 错误信息通常比较笼统，但仔细阅读仍能定位问题。以下是几种最常见的报错及原因：

  • "No 'Access-Control-Allow-Origin' header is present on the requested resource"：服务器响应中根本没有 Access-Control-Allow-Origin 头。最常见的原因是后端没配置 CORS，或者请求根本没到达目标服务器（被反向代理、防火墙拦截，返回了默认错误页）。
  • "The 'Access-Control-Allow-Origin' header has a value '...' that is not equal to the supplied origin"：服务器返回的允许源与请求的 Origin 不匹配。例如后端写死了 http://app.example.com，但前端实际是 https://app.example.com（协议不同）。
  • "The value of the 'Access-Control-Allow-Origin' header in the response must not be the wildcard '*' when the request's credentials mode is 'include'"：携带凭证时用了通配符 *，需改为具体域名。
  • "Method PUT is not allowed by Access-Control-Allow-Methods in preflight response"：预检响应的 Access-Control-Allow-Methods 没有包含实际请求使用的方法。
  • "Request header field Authorization is not allowed by Access-Control-Allow-Headers in preflight response"：预检响应的 Access-Control-Allow-Headers 没有包含前端使用的自定义头。
  • "Response to preflight request doesn't pass access control check: Redirect is not allowed for a preflight request"：预检请求被服务器重定向（如 HTTP 跳 HTTPS），浏览器不允许预检请求被重定向。

一个高频的"假 CORS 错误"值得注意：当后端代码抛出异常导致服务器返回 500 错误页，而错误页没有配置 CORS 头时，浏览器会报"No 'Access-Control-Allow-Origin' header"，让人误以为是 CORS 配置问题，实则是后端业务逻辑出错。遇到这种情况，要直接看服务器日志，而不是死磕 CORS 配置。

七、如何修复 CORS 错误：各技术栈实战配置

修复 CORS 错误的核心原则是：在后端（被访问的资源服务器）正确配置 CORS 响应头。下面给出主流技术栈的配置示例。

1. Nginx 配置

Nginx 作为反向代理时，可以在代理层统一处理 CORS，避免改动后端代码：

server {
    listen 80;
    server_name api.example.com;

    # 处理预检请求
    if ($request_method = 'OPTIONS') {
        add_header 'Access-Control-Allow-Origin' 'https://app.example.com' always;
        add_header 'Access-Control-Allow-Methods' 'GET, POST, PUT, DELETE, OPTIONS' always;
        add_header 'Access-Control-Allow-Headers' 'Content-Type, Authorization, X-Requested-With' always;
        add_header 'Access-Control-Max-Age' 86400 always;
        add_header 'Content-Type' 'text/plain; charset=utf-8';
        add_header 'Content-Length' 0;
        return 204;
    }

    # 普通请求添加 CORS 头
    add_header 'Access-Control-Allow-Origin' 'https://app.example.com' always;
    add_header 'Access-Control-Allow-Credentials' 'true' always;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

注意 always 参数确保错误响应也带上 CORS 头。如果需要支持多域名动态回显 Origin，可以用变量：

map $http_origin $cors_origin {
    default "";
    "~^https?://(.*\.)?example\.com$" "$http_origin";
}
server {
    add_header 'Access-Control-Allow-Origin' $cors_origin always;
    # ...
}

2. Apache 配置

Apache 通过 mod_headers 模块配置 CORS：

<IfModule mod_headers.c>
    # 允许的源
    Header set Access-Control-Allow-Origin "https://app.example.com"
    Header set Access-Control-Allow-Credentials "true"
    Header set Access-Control-Allow-Methods "GET, POST, PUT, DELETE, OPTIONS"
    Header set Access-Control-Allow-Headers "Content-Type, Authorization"
    Header set Access-Control-Max-Age "86400"
</IfModule>

# 处理 OPTIONS 预检请求，直接返回 204
RewriteEngine On
RewriteCond %{REQUEST_METHOD} OPTIONS
RewriteRule ^(.*)$ $1 [R=204,L]

3. Node.js (Express)

Express 推荐使用官方的 cors 中间件，简洁且功能完整：

const express = require('express');
const cors = require('cors');
const app = express();

// 允许单个域名，并支持携带凭证
const corsOptions = {
    origin: 'https://app.example.com',
    credentials: true,
    optionsSuccessStatus: 204,
    methods: ['GET', 'POST', 'PUT', 'DELETE', 'OPTIONS'],
    allowedHeaders: ['Content-Type', 'Authorization']
};
app.use(cors(corsOptions));

app.get('/api/data', (req, res) => {
    res.json({ msg: 'CORS 已配置' });
});

app.listen(3000);

如果不想用中间件，也可以手动设置：

app.use((req, res, next) => {
    res.header('Access-Control-Allow-Origin', 'https://app.example.com');
    res.header('Access-Control-Allow-Credentials', 'true');
    res.header('Access-Control-Allow-Methods', 'GET, POST, PUT, DELETE, OPTIONS');
    res.header('Access-Control-Allow-Headers', 'Content-Type, Authorization');
    if (req.method === 'OPTIONS') {
        return res.sendStatus(204);
    }
    next();
});

4. Spring Boot (Java)

Spring Boot 提供了 @CrossOrigin 注解和全局配置两种方式。推荐使用全局 WebMvcConfigurer：

@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("https://app.example.com")
                .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
                .allowedHeaders("Content-Type", "Authorization")
                .allowCredentials(true)
                .maxAge(86400);
    }
}

如果使用了 Spring Security，还需在安全配置中启用 CORS：

@Configuration
@EnableWebSecurity
public class SecurityConfig {
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http.cors(cors -> cors.configurationSource(corsConfigurationSource()))
            // ...其他安全配置
            ;
        return http.build();
    }

    @Bean
    public CorsConfigurationSource corsConfigurationSource() {
        CorsConfiguration config = new CorsConfiguration();
        config.setAllowedOrigins(List.of("https://app.example.com"));
        config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
        config.setAllowedHeaders(List.of("Content-Type", "Authorization"));
        config.setAllowCredentials(true);
        config.setMaxAge(86400L);

        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/**", config);
        return source;
    }
}

这是 Spring Boot 中最常见的"坑"：只配了 WebMvcConfigurer 却忘了在 Security 里启用 CORS，导致预检请求被安全过滤器拦截。

5. 开发环境临时方案：代理

在本地开发时，前后端常运行在不同端口（如前端 localhost:5173，后端 localhost:3000）。比起让后端配 CORS，更优雅的做法是用开发服务器的代理功能，把请求伪装成同源：

Vite 配置（vite.config.js）：

export default {
    server: {
        proxy: {
            '/api': {
                target: 'http://localhost:3000',
                changeOrigin: true
            }
        }
    }
};

这样前端请求 /api/data 会由 Vite 转发到 http://localhost:3000/api/data，浏览器看到的始终是同源请求，根本不会触发 CORS。注意这只是开发环境方案，生产环境仍需在后端或网关层正确配置 CORS。

八、CORS 排查步骤清单

遇到 CORS 错误时，按以下步骤系统排查，能快速定位问题：

  1. 确认是否真的是 CORS 问题：打开浏览器开发者工具 Network 面板，查看失败的请求。如果是预检 OPTIONS 请求失败，先单独分析它；如果是普通请求失败，查看响应头。注意：网络超时、SSL 证书错误也会被误报为 CORS 错误，因为浏览器拿不到响应头。
  2. 检查请求的 Origin：在请求头中找到 Origin，确认它的协议、域名、端口。很多人栽在 http 与 https、www 与不带 www、尾随斜杠的差异上。
  3. 检查响应头：看响应中是否有 Access-Control-Allow-Origin，其值是否与 Origin 完全匹配。用 SiteCheck 的 HTTP 头检测工具可以快速查看。
  4. 区分预检与简单请求：如果存在 OPTIONS 请求，重点检查预检响应的 Access-Control-Allow-Methods 和 Access-Control-Allow-Headers 是否覆盖了实际请求用到的内容。
  5. 检查凭证配置一致性：如果前端用了 credentials: 'include'，后端必须有 Access-Control-Allow-Credentials: true，且 Access-Control-Allow-Origin 不能是 *。
  6. 检查后端是否真的处理了请求：CORS 错误有时是后端 500 异常的"伪装"。查看后端日志，用 curl -H "Origin: https://app.example.com" -I https://api.example.com/api/data 直接测试响应头。
  7. 检查中间件/过滤器顺序：在 Spring Security、.NET 等框架中，CORS 中间件必须在认证之前执行，否则预检请求会被拦截返回 401。
  8. 检查反向代理与 CDN：Nginx、Cloudflare 等 CDN 可能缓存了不带 CORS 头的响应，或剥离了 CORS 头。配置 Vary: Origin 可防止缓存错乱——当不同 Origin 的请求命中同一资源缓存时，Vary: Origin 提示缓存按 Origin 区分。

九、CORS 安全风险与最佳实践

CORS 本身是安全机制，但配置不当会引入安全风险。以下是几条最佳实践：

1. 避免使用通配符 *。 虽然 Access-Control-Allow-Origin: * 配置简单，但它意味着任何网站都能读取你的接口响应。对于公开的、无敏感数据的 API（如天气查询）尚可，但涉及用户数据的接口绝不能用通配符。应明确列出允许的域名。

2. 不要把 CORS 当作唯一防线。 前文强调过，CORS 是浏览器执行的机制，限制的是"浏览器读取响应"。攻击者完全可以绕过浏览器，用 curl、服务端脚本直接发请求。真正的鉴权必须依赖后端的会话验证、Token 校验、API Key 等机制。CORS 只是阻止"正常浏览器中的恶意脚本"，不是访问控制的替代品。

3. 谨慎对待 Access-Control-Allow-Origin: null。 某些情况（如本地文件 file://、沙箱 iframe）下 Origin 会是 null。如果后端把 null 加入允许列表，可能被攻击者构造 null Origin 的页面利用。建议禁止 null Origin。

4. 动态回显 Origin 时要做白名单校验。 为了支持多域名，有些后端直接把请求的 Origin 原样回显到 Access-Control-Allow-Origin。如果没有任何校验，等于允许任意源访问。正确做法是维护一个允许域名白名单，只有 Origin 命中白名单才回显。

5. 正确配置 Vary: Origin。 当服务器根据请求的 Origin 返回不同的 Access-Control-Allow-Origin 时，必须加上 Vary: Origin 响应头。否则 CDN 或浏览器缓存可能把 A 域名请求的响应缓存下来返回给 B 域名，导致 CORS 头不匹配而报错。

6. 缩小 CORS 作用范围。 只对需要跨域访问的路径（如 /api/）配置 CORS，而不是全站开放。限制允许的方法和头部到实际需要的最小集合。

十、总结

CORS 不是 Bug，而是浏览器为保护用户数据而设计的精密安全机制。它的核心逻辑是：服务器通过响应头声明"我允许哪些源访问"，浏览器据此决定是否把响应交给前端 JavaScript。理解同源策略、简单请求与预检请求的区别、各核心响应头的含义，是正确配置和排查 CORS 问题的基础。

解决 CORS 错误的关键始终是在后端正确配置响应头，而非在前端"绕过"。记住几个要点：携带凭证时不能用通配符 *；预检请求是 OPTIONS，后端必须正确响应；CORS 限制的是"读"不是"写"，鉴权要靠后端；配置不当的 CORS 反而会成为安全漏洞。开发环境可用代理绕过，生产环境务必在后端或网关层规范配置。

下次再看到那行红色的 CORS 报错，不要慌张——打开开发者工具，检查 Origin 与响应头，按本文的排查清单一步步分析，绝大多数 CORS 问题都能在几分钟内解决。如果你想检查自己网站的 HTTP 响应头配置是否正确，可以使用 SiteCheck 的 HTTP 头检测工具，快速定位缺失或错误的 CORS 头部。
